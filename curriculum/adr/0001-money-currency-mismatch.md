# ADR 0001: Money-Currency Mismatch
## Status: Accepted
## Context
In our loan servicing domain, we have a `Money` class that represents an amount of money along with its associated currency. The `Currency` is typically represented using ISO 4217 currency codes (e.g., USD, EUR). When performing operations on `Money` instances, such as addition or subtraction, we need to ensure that the currencies match. If they do not match, we need to decide how to handle this situation.
In a way this is a common problem in financial applications, and there are several approaches to handle it. The main options we are considering are:
1. **Throw an exception**: If an operation is attempted between two `Money` instances with different currencies, we could throw a runtime exception (e.g., `CurrencyMismatchException`). This
2. would immediately signal to the developer that they are trying to perform an invalid operation, but it could lead to runtime errors if not handled properly.
3. **Return an `Optional`**: Instead of throwing an exception, we could return an `Optional<Money>` that is empty if the currencies do not match. This would allow the caller to handle the mismatch gracefully, but it could lead to more verbose code and potential misuse if the caller forgets to check for the empty case.
4. **Introduce a result type**: We could create a custom result type (e.g., `MoneyOperationResult`) that encapsulates the success or failure of the operation, along with any relevant error messages. This would provide a clear contract for the operation, but it might add complexity to the codebase and require additional boilerplate.
5. **Prevent the operation earlier**: We could design our API in such a way that it prevents the possibility of performing operations on `Money` instances with different currencies in the first place. For example, we could require that all `Money` instances involved in an operation must be of the same currency, and enforce this through the type system or by providing factory methods that ensure currency consistency. This would be the most robust solution, but it might require significant changes to our existing codebase and could limit flexibility in certain scenarios (e.g., when we want to perform currency conversions).
6. Each of these approaches has its own trade-offs in terms of safety, usability, and complexity. We need to carefully consider our domain requirements and the typical use cases for our `Money` class to determine which approach is the best fit for our application.
## Decision
The decision is to **throw an exception** when an operation is attempted between two `Money` instances with different currencies.
This was decided in order to keep the domain pure and then the application service catches, fetches rate, converts, retries. This way we don't have to deal with `Optional` or result types in the domain, and we can ensure that any currency mismatches are immediately visible and handled appropriately by the application layer as it is a  coordination of fetch-convert-retry is orchestration, not business logic.
## Consequences
- Developers will need to handle `CurrencyMismatchException` when performing operations on `Money` instances, which may require additional error handling code.
- This approach will help prevent silent errors and ensure that developers are aware of currency mismatches, leading to more robust and reliable financial calculations.
- Application layer now has a coordination responsibility it didn't have before - it needs to ensure that all `Money` instances involved in an operation are of the same currency, or handle the exception if they are not. This may require additional logic in the application layer to manage currency consistency and conversions when necessary. On the other hand, on a functional side it allows a customer to either accept the transaction with the default exchange rate or reject it, which is a more realistic scenario in financial applications.
- We will need to update our documentation and provide clear guidelines on how to handle currency mismatches when working with the `Money` class to ensure that developers understand the implications of this decision and how to properly use the `Money` class in their code.
- What happens when the exchange rate fetch fails after Money already threw? You have a two-step operation that can fail mid-way. This is a potential downside of this approach, as it introduces additional complexity in handling the failure of the exchange rate fetch after the `Money` class has already thrown an exception. We will need to ensure that our application layer is designed to handle this scenario gracefully, potentially by implementing retry logic or providing fallback mechanisms in case the exchange rate fetch fails.
